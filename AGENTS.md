- CRM de representantes: tabelas crm_* referenciam profiles (representante = profiles.tipo_vendedor='representante'); acesso por crm_is_gestao() (admin/master/gestao_representantes) ou representante_id = auth.uid(). Why: estende o mesmo modelo de clientes sem tocar tabelas existentes.
- Sales availability and quantity routing are centralized in classifyItem; every order/provision write still verifies catalog membership through salesStock with the normal client. Why: commercial release must apply consistently without inventing physical stock or bypassing catalog access.
- CRM: nomes de representantes vêm da função crm_representantes_lista() (security definer: gestão vê todos, representante só a si). Why: evita abrir profiles para o papel gestao_representantes. Régua é calculada na tela (src/lib/crm.ts), nunca gravada.
- CRM Parte 3: pedidos/cotações do lead são lidos pelo cliente normal (RLS de orders/cotacoes), nunca por função privilegiada; a automação "Pedido fechado" é o trigger AFTER INSERT em orders, que só altera crm_leads. Why: o CRM só lê e linka, sem tocar nos fluxos comerciais.
- Mapa de atuação: os dados moram no Fetély Connect (https://fetely-rep-connect.lovable.app); o Order Pro só lê via src/lib/mapaAtuacao.functions.ts (GET /api/public/mapa-atuacao, POST /api/public/vincular-representante, GET /api/public/atividades-representantes, POST /api/public/tarefa-representante; header X-Mapa-Token do secret MAPA_ATUACAO_TOKEN). Why: a rede de representantes é gerida no Connect; aqui só exibimos e vinculamos usuários.
- Balcão B2C (/venda-b2c): todo dado da Venda Direta passa pelo branch balcao_* da edge enviar-para-sncf, que injeta a identidade do vendedor pelo login (fop_profile_id/vendedor_email/vendedor_nome) e repassa status/corpo do SNCF sem traduzir erro. Nenhuma tabela do FOP guarda cliente ou pedido B2C. Why: o comercial não tem sessão no SNCF e a autoridade da venda direta é a esteira do SNCF.
- B2C creation and editing reuse NovoPedidoTab with presentation cards and pure basic-validation helpers; save coordination remains in salvarAlteracaoBalcao, and expedition instructions are prefixed in observacao rather than introducing a bridge field. Why: preserve prefilled data, existing calls and SNCF authority while matching the shared mobile sales workflow.
- Cart-to-B2C transfer is a read-only SKU/unit-quantity projection, consumed once through history state/session storage and resolved through SNCF after default-CD loading. Why: retail pricing and stock must not inherit or modify any B2B store, negotiation, calculation or order flow.
- B2C immediate-sale presentation is inferred only from exclusive balcao quote options and retained per CD during recalculation and next-sale reset; payment declarations use the existing authenticated bridge with original errors. Why: keep event handling independent of warehouse codes and preserve non-event flows without local commercial authority.
- B2C stock is an isolated read-only tab using balcao_cds and balcao_estoque through useBalcao, with Query caches scoped by user and CD and pure frontend filtering/sorting. Why: SNCF remains the stock authority and stock browsing cannot change order forms or write commercial data.
- Bonification payment detection is shared by form selection and order serialization; the extraction trigger and SNCF outbound bridge must agree on nonchargeable payments, while Balcão retains its SNCF bonification discriminator. Why: creation, editing and quotation conversion must agree without changing pricing calculations or the B2C API contract.
- Sent B2B adjustments use the authenticated forwarding bridge and a separate cart branch driven exclusively by SNCF permissions; they never call local order, quotation or provision creation. Why: SNCF owns adjustment authority and must not receive duplicate orders.
- SNCF read queries decode bridge errors through the shared helper and render failures locally with explicit retry rather than throwing to the page boundary or treating an outage as an empty result. Why: external configuration/schema failures must not blank the sales screens.
- Catalog spreadsheets parse paginated raw database rows and persist allowlisted Product patches through the same awaited catalogStore persistence helper as the editing dialog, with per-product audit. Why: preserve Operations and phase, retain database gates/history/sync and report actual failures.
- SharePoint daily review lives only in SNCF; FOP receives authenticated writes through the shared catalogSharepoint handler and shared importer field resolution/persistence. Why: one review screen, consistent validation/audit and unchanged outbound triggers.
- External callers use `/api/public/catalogo-planilha-aplicar`; the requested `/api/catalogo-planilha-aplicar` shares its handler, verifying FSNC_INBOUND_TOKEN from Vault before writes. Why: bypass hosting login without bypassing integration authentication.
- Fiscal fields (ncm, cest, origem_fisc, origem_prod) are writable only through the SNCF catalog door via FISCAL_FIELDS and the `allowed` parameter of saveProductFields; PRODUCT_FIELDS, the manual importer, template and edit dialog keep them read-only. Why: SNCF owns fiscal review while manual product edits must not change fiscal data.
- External audit actors remain in campos_alterados.quem; usuario_id is null unless the SNCF UUID exists in FOP profiles. Why: preserve identity without violating the existing audit foreign key or inventing profiles.
- SNCF-created catalog dimensions enter through `/api/public/catalogo-dimensao-criar`; only collections are accepted, matched idempotently by case/accent/space-insensitive names, with new rows audited as `planilha_sharepoint`. Why: one-click SNCF review creates canonical FOP dimensions without duplicate spellings.
- Photo management uses photoProducts to exclude rows without named collection/category from both tabs without mutating catalog data. Why: incomplete dimensions must not crash sorting or create invalid photo upload keys.
- Catalog configuration and permission overrides use admin/master-scoped reads; public tracking uses existing RPCs, saved-cart reads require sales roles and representative ownership, and catalog file access uses the active-catalog proxy instead of public bucket listing. Why: protect configuration, access keys, sessions and customer carts without removing public catalog delivery.
